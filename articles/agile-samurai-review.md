## はじめに

自分のチームの開発手法を一言で表すのが難しい。ウォーターフォールほど厳密に工程が分かれているわけではないが、アジャイルを実践しているとも言い切れない。なんとなく動いてはいるけど、どこかうまくいっていない感覚がある——そういう状態で、「もしかしたら自分たちの課題に関係する何かがあるかもしれない」と思って手に取ったのが本書だった。

結果として、手法の話よりも「なぜその手法が必要なのか」の説明が充実していて、自分たちの開発に当てはめながら読める本だった。本記事は各章の内容をまとめた読書メモ＋感想。著作権に配慮して概念の紹介にとどめ、個人的に特に刺さったポイントを中心に書いていく。

## 特に印象に残ったテーマ

### 1. アジャイルの三つの真実

本書の序盤で提示される前提が刺さった。

- プロジェクト開始時点で要求をすべて確定することはできない
- 要求は必ず途中で変化する
- やるべきことは常に時間とリソースを上回る

この3点を前提として受け入れることで、なぜ変化に対応できる仕組みが必要なのかがスッと入ってきた。アジャイルが「スプリントで開発する手法」というよりも、もっと根本的な考え方から来ているものだと整理できた感じがした。

---

### 2. インセプションデッキ——プロジェクト開始前にやること

本書でもっとも実用的だと感じたのがこのパート。

プロジェクトを始める前に、チーム全員で答えておくべき10の問いをまとめたフレームワーク。「なぜこのプロジェクトをやるのか」「30秒で説明するとどうなるか」「やらないことは何か」「関係者は誰か」「どんなリスクがあるか」といった問いに、関係者全員が同じ答えを持っている状態を作ることを目的としている。

特に面白かったのが「やらないことリスト」の考え方。「やること」を決めるより「やらないこと」を明示する方が難しい。でも明示しておかないと、後になって「あれはやってくれると思っていた」というすれ違いが起きる。「後で決める」という列を設けて曖昧なものを曖昧なまま放置しない、というのは実務でもすぐ使えると思った。

また「ご近所さんを探せ」という問いも印象的だった。開発が進んだタイミングでアーキテクチャレビューやセキュリティ確認を求めてくるグループが突然現れてスケジュールが狂う——という経験は多くの現場で起きていると思う。事前にそういった関係者を洗い出して、関与タイミングを計画に組み込んでおくという発想は地味だが効果的だ。

---

### 3. スコープを動かすという発想

アジャイルの計画論として印象的だったのが「時間・予算・品質は固定し、スコープを柔軟に扱う」という考え方。

「トレードオフスライダー」という可視化ツールを使って、どの要素を優先するかをチームと顧客で合意しておく。スコープを動かすという発想は顧客には受け入れられにくいことが多いが、事前に「何かを諦めなければ何かが守れない」というトレードオフの現実を共有しておくことで、後の調整がしやすくなる。

これは実務でも実感がある。現在の進捗（残作業量やベロシティ）を数字で可視化して顧客に共有しておくと、新しい機能追加の要望が来たときに「これを入れるなら何を後回しにするか選んでください」という交渉が自然にできる。数字がないと感情的な押し引きになりがちだが、現状のキャパシティが見えていれば顧客自身に優先度を決めてもらえる。スライダーを「顧客に回させる」というのは、この構造を作るための道具だと理解した。

---

### 4. 技術プラクティス——テスト・TDD・CI

後半の技術パートは、普段のコーディングに直結する内容だった。

**ユニットテストの本質**

テストを書く一番の価値は「自信をもってコードを変更できること」だと本書は説く。リファクタリング時も、既存機能を壊していないと即確認できる仕組みがあるかどうかで、変更のコストがまったく変わる。

これは身に覚えがある。以前、エディタ上で不要に見えた CSS のクラス名を削除したら、テストがなかったので動くまで気づかず、リリース後に不具合として発覚した。テストがあれば最低限リリース前に検知できていた。

**TDD（テスト駆動開発）**

「失敗するテストを書くまで新しいコードを一切書かない」というルール。最大のメリットは、テストを先に書くことで「このコードをどう使うか」を最初に決めることになり、テストしやすい＝使いやすい設計に自然と近づいていくことだ。

**継続的インテグレーション**

作業単位を小さくして、頻繁にインテグレーションすることの重要性が説かれる。変更を長期間ブランチで抱えると、mainとの差分が大きくなりマージ時に問題が集中する。小さく頻繁に統合することで、問題の原因特定が容易になる。

これは経験として痛感している。3ヶ月ごとのまとめリリースという体制だと、複数人が長期間別々のブランチで並行開発して、最後にまとめてマージするという流れになりがちだ。その結果、コンフリクトが大量に発生する上に、何ヶ月も前に書いたコードの意図を思い出せないという状況に陥る。「あのとき何を意図してこう書いたんだっけ」という状態でコンフリクト解消をするのは、かなりリスクが高い。

## 感想

書いてあることはどれも理解できる。「やらないことを明示しろ」「進捗を数字で見せろ」「小さく頻繁にインテグレーションしろ」——どれも正しいと思う。ただ、いざ実践しようとすると壁があることも感じる。顧客を巻き込むのも、スコープ交渉をするのも、理解と実行の間には結構な距離がある。

一方で、試せそうなところから動いてはいる。最近、顧客とのやりとりを GitHub の Issues と Projects で管理し始めた。バックログを可視化して、進捗を共有して、優先順位を一緒に決める——というのが本書で言っていることに近い形で少しずつできてきた。完全なアジャイルではないにしても、「現状を数字で見せながら顧客と対話する」という感覚はつかめてきた気がしている。

そもそも本書には「自分たちがアジャイルかどうかを確認する方法なんてない」という趣旨の記述があった。アジャイルであることが目的ではなく、毎週価値ある成果を届けられているか、そのための弛まぬ努力を続けられているか——それがアジャイルらしいということらしい。「うちはアジャイルなのか」という問いの立て方自体がずれていたのかもしれない。
