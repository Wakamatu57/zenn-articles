## はじめに

「ソフトウェアアーキテクチャの基礎」を読んだ。

全26章・500ページ超のボリュームで、アーキテクチャ特性・スタイル・パターンから、ADRやリスク分析・チームマネジメントといったアーキテクトのソフトスキルまでを体系的にカバーする一冊だ。

本記事は読書まとめ＋感想。前半は技術的に印象に残った概念の整理、後半は感想を書く。

---

## アーキテクチャとは何か

本書の出発点となる定義が面白い。

> **「重要なもの全て、それが何であれ」**（Ralph Johnson）

アーキテクチャとは「後から変えるのが難しい決定」であり、アーキテクトの仕事とは「構造・特性・決定・原則の4つを設計すること」と定義されている。

特に印象的だったのは、**「アーキテクチャかどうか」の判断基準**だ。

- 構造に影響を与えるか
- アーキテクチャ特性に影響を与えるか
- システムの原則に関わるか

「データベースにPostgreSQLを使う」はアーキテクチャ的な決定だが、「このクラスでどのデザインパターンを使うか」は設計上の決定であり、アーキテクチャではない。この区別が本書全体の軸になっている。

---

## アーキテクチャ特性という考え方

「機能要件」ではなく「システムがどうあるべきか」を表すのがアーキテクチャ特性（いわゆる非機能要件）だ。

本書では以下のように分類される。

| カテゴリ | 例 |
|---------|-----|
| 運用上 | 可用性・スケーラビリティ・パフォーマンス・耐障害性 |
| 構造上 | モジュール性・デプロイ容易性・テスト容易性 |
| 横断的 | セキュリティ・オブザーバビリティ・法規制準拠 |

重要なのは、**全ての特性を同時に最大化することは不可能**だという点だ。可用性を上げれば複雑性が増す。スケーラビリティを重視すれば整合性の担保が難しくなる。アーキテクトの仕事は「何を犠牲にして何を得るか」のトレードオフを判断することに尽きる。

「最もサポートしなければならないアーキテクチャ特性を3つ以内に絞れ」という本書の主張は、優先度のない特性リストが機能しない実態を突いていると感じた。

## 主なアーキテクチャスタイルの整理

本書の中核をなすのがアーキテクチャスタイルの比較だ。モノリスから分散まで8つ以上のスタイルが網羅されている。

### モノリス系

| スタイル | 特徴 |
|---------|------|
| レイヤードアーキテクチャ | 技術で分割（プレゼンテーション・ビジネス・永続化）。暗黙のアーキテクチャになりやすい |
| モジュラーモノリス | ドメインで分割しながら単一デプロイを維持。マイクロサービスへの移行パスとして有効 |
| マイクロカーネル | コアシステム＋プラグインの構成。拡張性が高く、VSCode・Eclipseが典型例 |
| パイプライン | フィルターとパイプで処理を一方向に接続。ETLや変換処理向き |

### 分散系

| スタイル | 特徴 |
|---------|------|
| サービスベース | マイクロサービスより粒度が大きい。DBを共有できる柔軟性あり |
| イベント駆動 | 非同期・ファイアアンドフォーゲット型。拡張性が高く時間的結合を切れる |
| スペースベース | タプルスペース経由でインメモリ共有。高スケーラビリティが必要な場面向き |
| マイクロサービス | 境界づけられたコンテキスト単位。サービスごとにDB・独立デプロイが原則 |

スタイルを選ぶ際の判断軸として本書が提示するのは「**スタイルの違いはドメインではなく、サポートすべきアーキテクチャ特性の違い**」という視点だ。ECサイトと社内ツールが同じ機能でも選ぶスタイルが変わるのは、スケーラビリティや可用性への要求が異なるからだ。

## アーキテクチャパターン

スタイルが「システムの全体構造」であるのに対し、パターンは「特定の問題への解法」だ。

### CQRS

書き込み（Command）と読み取り（Query）でモデルを分離するパターン。

```
Command側（書き込み）         Query側（読み取り）
┌────────────────┐  非同期  ┌────────────────────┐
│ 正規化モデル     │ ──────→ │ 非正規化ビュー        │
│ 整合性・検証重視  │          │ JOIN済み・計算済み     │
│ RDS など         │          │ DynamoDB/OpenSearch │
└────────────────┘          └────────────────────┘
```

読み取りが書き込みより圧倒的に多く、JOINが重いシステムで効果を発揮する。結果整合性を受け入れる設計が前提になる。

### サービスメッシュ

マイクロサービス間の横断的関心事（認証・mTLS・サーキットブレーカー・可観測性）をアプリのコードから分離してインフラ層で管理する仕組み。

サイドカー（各サービスと同じPod内に配置する補助コンテナ）をコントロールプレーンで一元管理する構成が基本だ。

### サガパターン

サービス間トランザクションを「各サービス内のローカルトランザクション」に分割し、失敗時は補償トランザクションで打ち消す仕組み。分散システムでACIDを維持するコストを避けつつ整合性を保つアプローチ。

## アーキテクト思考・ソフトスキル

後半では技術的な話から離れ、アーキテクトとして働く上でのソフトスキルが扱われる。これが想定外に充実していた。

### ADR（Architecture Decision Record）

アーキテクチャ決定を記録するための軽量なドキュメント形式。タイトル・ステータス・コンテキスト・決定・影響で構成される。

何をADRに書くべきかについて、本書の答えが的確だった。

> 「アーキテクチャの変更かどうか」より「後から『なぜこうしたんだっけ』と聞かれて答えるのに苦労する意思決定かどうか」

グラウンドホッグデーアンチパターン（同じ議論が何度も繰り返される）の解決策としてADRが機能する。

### リスクストーミング

チームで「識別→合意→軽減」の3フェーズでアーキテクチャ上のリスクを洗い出す手法。**一度に一つの観点（可用性のみ、パフォーマンスのみ）に絞る**のがポイントで、複数の視点を同時に扱うと見落としが増える。

### 多元的無知

「会議で誰も反対しないが、実は全員が内心で納得していない」状態を多元的無知（Pluralistic Ignorance）と呼ぶ。心理的安全性の欠如が原因で、アーキテクトが「疑問を歓迎する」雰囲気を作ることが解決策になる。

## 読んで感じたこと

### よかった点

**「なぜそのスタイルを選ぶか」の判断軸が手に入る**

各アーキテクチャスタイルを「これが正解」として提示するのではなく、常にトレードオフとセットで説明している。「スケーラビリティは強いが応答性は低い」「耐障害性は高いが運用複雑性が増す」という形式で各スタイルが整理されるので、設計判断の引き出しとして使いやすい。

**技術だけで終わらない**

後半のADR・リスクストーミング・交渉・チームマネジメントの章が意外と充実していた。アーキテクトを「技術的意思決定者」としてではなく「チームと組織に働きかける役割」として捉えている点が、現実の仕事感覚に近かった。

### 難しかった点

**スタイルの数が多くて整理が大変**

8種類以上のスタイルが登場し、それぞれのトレードオフを覚えながら読み進めるのは骨が折れた。章ごとにメモを取りながら読んだことで何とか整理できたが、受け身で読んでいると後半に進むほど前の内容が薄れていく。

**コナーセンスは難易度が高い**

静的コナーセンス・動的コナーセンスといった設計結合度の概念は理解の難易度が高かった。「なぜそれが重要なのか」はわかるが、実際のコードでどう評価するかは経験が必要だと感じた。

---

## まとめ

「アーキテクチャスタイルは知っているが、どう選ぶかわからない」という状態に刺さる一冊だった。

各スタイルの特性・トレードオフを比較しながら選ぶための視点が得られ、設計判断の場面で「このシステムに本当に必要なアーキテクチャ特性は何か」から考えるクセがついた気がする。

ソフトスキルの章も含めて、アーキテクトという役割の全体像を掴みたい人にはおすすめの一冊。
