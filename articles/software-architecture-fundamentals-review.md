## はじめに

「ソフトウェアアーキテクチャの基礎」を読んだ。

AIエージェントの普及によって、開発者一人がカバーする範囲が広がっている。社内アプリであればフロント・バック・インフラをひとりで担当するケースも珍しくなくなってきた。実装はAIに任せる分、自分たちに求められるのはインフラ構成の判断・コードレビュー・セキュリティの担保など、より上位の視点だと感じている。いわばAIエージェント（開発者）のレビュアーとしてアーキテクト的な視点が必要になってきた、というのが本書を手に取ったきっかけだ。

全27章・500ページ超のボリュームで、アーキテクチャ特性・スタイル・パターンから、ADRやリスク分析・チームマネジメントといったアーキテクトのソフトスキルまでを体系的にカバーする一冊だ。

本記事は読書まとめ＋感想。前半は技術的に印象に残った概念の整理、後半は感想を書く。

---

## アーキテクチャとは何か

本書はアーキテクチャを4つの要素で定義する。

- **アーキテクチャスタイル** — システム全体の構造パターン（マイクロサービス、レイヤードなど）
- **アーキテクチャ特性** — システムが満たすべき品質属性（可用性・スケーラビリティ・セキュリティなど）
- **論理コンポーネント** — システムを構成する機能単位の区切り方
- **アーキテクチャ決定** — 制約・ルールとして機能する設計上の選択（変更コストが高いもの）

アーキテクチャと設計の区別は、以下の3軸で判断する。

1. 戦略的 or 戦術的な判断か
2. 変更・構築にかかる労力の大きさ
3. トレードオフの重要度

「データベースにPostgreSQLを使う」はアーキテクチャ的な決定だが、「このクラスでどのデザインパターンを使うか」は設計上の決定だ。

### アーキテクチャに正解はない、あるのはトレードオフだけ

> 「アーキテクチャには正解も不正解もない。あるのはトレードオフだけだ」

この主張が本書全体を貫く軸になっている。設計の答えは文脈依存であり、どのスタイルにもメリットとデメリットが存在する。

例えば、メッセージング方式の選択一つとっても：

| 方式 | メリット | デメリット |
|------|---------|-----------|
| パブサブ（トピック方式） | 疎結合・スケールしやすい | データアクセス制御・セキュリティ境界の設定が難しい、固有のコントラクトを持てない |
| キューを使ったサービス間通信 | セキュリティ・契約が明確 | 結合度が上がる |

アーキテクトの仕事は「正解を選ぶこと」ではなく、「今の制約の中で最善のトレードオフを選ぶこと」だ。

## アーキテクチャ特性という考え方

「機能要件」ではなく「システムがどうあるべきか」を表すのがアーキテクチャ特性だ。

本書では以下のように分類される。

| カテゴリ | 例 |
|---------|-----|
| 運用上 | 可用性・スケーラビリティ・パフォーマンス・耐障害性 |
| 構造上 | モジュール性・デプロイ容易性・テスト容易性 |
| 横断的 | セキュリティ・オブザーバビリティ・法規制準拠 |

重要なのは、**全ての特性を同時に最大化することは不可能**だという点だ。可用性を上げれば複雑性が増す。スケーラビリティを重視すれば整合性の担保が難しくなる。アーキテクトの仕事は「何を犠牲にして何を得るか」のトレードオフを判断することに尽きる。

「最もサポートしなければならないアーキテクチャ特性を3つ以内に絞れ」という本書の主張は、優先度のない特性リストが機能しない実態を突いていると感じた。

## 主なアーキテクチャスタイルの整理

本書の中核をなすのがアーキテクチャスタイルの比較だ。モノリスから分散まで8つ以上のスタイルが網羅されている。

### モノリス系

| スタイル | 特徴 |
|---------|------|
| レイヤードアーキテクチャ | 技術で分割（プレゼンテーション・ビジネス・永続化）。暗黙のアーキテクチャになりやすい |
| モジュラーモノリス | ドメインで分割しながら単一デプロイを維持。マイクロサービスへの移行パスとして有効 |
| マイクロカーネル | コアシステム＋プラグインの構成。拡張性が高く、VSCode・Eclipseが典型例 |
| パイプライン | フィルターとパイプで処理を一方向に接続。ETLや変換処理向き |

### 分散系

| スタイル | 特徴 |
|---------|------|
| サービスベース | マイクロサービスより粒度が大きい。DBを共有できる柔軟性あり |
| イベント駆動 | 非同期・ファイアアンドフォーゲット型。拡張性が高く時間的結合を切れる |
| スペースベース | タプルスペース経由でインメモリ共有。高スケーラビリティが必要な場面向き |
| マイクロサービス | 境界づけられたコンテキスト単位。サービスごとにDB・独立デプロイが原則 |

スタイルを選ぶ際の判断軸として本書が提示するのは「**スタイルの違いはドメインではなく、サポートすべきアーキテクチャ特性の違い**」という視点だ。ECサイトと社内ツールが同じ機能でも選ぶスタイルが変わるのは、スケーラビリティや可用性への要求が異なるからだ。

## アーキテクチャパターン

スタイルが「システムの全体構造」であるのに対し、パターンは「特定の問題への解法」だ。

### CQRS

書き込み（Command）と読み取り（Query）でモデルを分離するパターン。

```
Command側（書き込み）         Query側（読み取り）
┌────────────────┐  非同期  ┌────────────────────┐
│ 正規化モデル     │ ──────→ │ 非正規化ビュー        │
│ 整合性・検証重視  │          │ JOIN済み・計算済み     │
│ RDS など         │          │ DynamoDB/OpenSearch │
└────────────────┘          └────────────────────┘
```

読み取りが書き込みより圧倒的に多く、JOINが重いシステムで効果を発揮する。結果整合性を受け入れる設計が前提になる。

### サービスメッシュ

マイクロサービス間の横断的関心事（認証・mTLS・サーキットブレーカー・可観測性）をアプリのコードから分離してインフラ層で管理する仕組み。

サイドカー（各サービスと同じPod内に配置する補助コンテナ）をコントロールプレーンで一元管理する構成が基本だ。

### サガパターン

サービス間トランザクションを「各サービス内のローカルトランザクション」に分割し、失敗時は補償トランザクションで打ち消す仕組み。分散システムでACIDを維持するコストを避けつつ整合性を保つアプローチ。

## アーキテクト思考・ソフトスキル

後半では技術的な話から離れ、アーキテクトとして働く上でのソフトスキルが扱われる。これが想定外に充実していた。

### ADR（Architecture Decision Record）

アーキテクチャ決定を記録するための軽量なドキュメント形式。タイトル・ステータス・コンテキスト・決定・影響・コンプライアンス・備考で構成される。

何をADRに書くべきかについて、本書の答えが的確だった。

> 「アーキテクチャの変更かどうか」より「後から『なぜこうしたんだっけ』と聞かれて答えるのに苦労する意思決定かどうか」

具体的にはこういった判断がADR向きだ。

- 後で覆すのが大変な大きな変更コストを伴う決定
- 複数の選択肢があり、それぞれにトレードオフがあった
- チーム全体・将来のメンバーに影響を与え続ける
- 判断の背景（なぜ他の案を選ばなかったか）が時間で失われやすい

グラウンドホッグデーアンチパターン（同じ議論が何度も繰り返される）の解決策としてADRが機能する。

### リスクストーミング

チームで「識別→合意→軽減」の3フェーズでアーキテクチャ上のリスクを洗い出す手法。**一度に一つの観点（可用性のみ、パフォーマンスのみ）に絞る**のがポイントで、複数の視点を同時に扱うと見落としが増える。

リスクは「影響度 × 発生可能性」の2軸で定量化する。定性的な議論を高・中・低の共通言語に落とし込むことで、ステークホルダー間の合意形成が容易になる。

### 多元的無知

「会議で誰も反対しないが、実は全員が内心で納得していない」状態を多元的無知（Pluralistic Ignorance）と呼ぶ。心理的安全性の欠如が原因で、アーキテクトが「疑問を歓迎する」雰囲気を作ることが解決策になる。

## 読んで感じたこと

**「なぜそのスタイルを選ぶか」の判断軸が手に入る**

各アーキテクチャスタイルを「これが正解」として提示するのではなく、常にトレードオフとセットで説明している。「スケーラビリティは強いが応答性は低い」「耐障害性は高いが運用複雑性が増す」という形式で各スタイルが整理されるので、設計判断の引き出しとして使いやすい。

自分のチームではレイヤードアーキテクチャや（当時はそう呼ぶことすら知らなかった）サービスベースに近い社内アプリをいくつか開発している。コストや規模の観点からマイクロサービスはしばらくなさそうだが、「なぜこのスタイルを選んでいるのか」「次に規模が変わったらどのスタイルに移るか」を言語化できるようになった。

**技術だけで終わらない**

後半のADR・リスクストーミング・交渉・チームマネジメントの章が意外と充実していた。特にアーキテクトの決定はほとんどが反発を生むという指摘は腑に落ちた。顧客は安く早く作ってほしい。保守性やセキュリティはプロジェクトの失敗経験がない限りなかなか意識してもらえない。だからこそ交渉力が必要で、技術的な妥当性を先に話してからコスト・工数の観点に移るというテクニックは実践で使えると感じた。

**コナーセンスは難易度が高い**

静的コナーセンス・動的コナーセンスといった設計結合度の概念は理解の難易度が高かった。AIにコードを書かせて「動的コナーセンスを静的コナーセンスに引き上げる」例を実際に動かすことでなんとか掴めた感じがある。一周では理解しきれない領域なので、設計判断が必要な場面で都度引き返す使い方が現実的だと思う。

**ADRの考え方は今すぐ取り入れられる**

ADRを大袈裟なドキュメントとして捉えなくていい。「なぜRestではなく非同期にしているのか」「なぜバックエンドではなくフロント側でソートしているのか」——こういった判断をIssueやWikiに残しておくだけで、後から確認できる資産になる。AIエージェントがそのIssueを検索して文脈を把握することもできるので、記録の価値はこれからさらに上がる。

**AIが実装する時代に、アーキテクト的視点はより重要になる**

AIエージェントが実装を担うようになると、開発者に求められる仕事は「どう書くか」から「どう設計するか」にシフトしていく。AIはコードを書くのは得意だが、社内の事情・顧客のビジネス文脈・チームの制約を踏まえた設計判断は苦手だ。本書でも生成AIに関する言及があったが、同じ主張がされていた。

補助として使えば強力だが、アーキテクチャ特性を絞り込む判断・スタイルの選択・トレードオフの言語化といった最終的な意思決定は、様々な要素を抱えた人間が下すしかない。AIが書いたコードのレビュアーとしてアーキテクト的な視点が必要になってきたと感じているのも、そこに理由がある。

---

## まとめ

「アーキテクチャスタイルは知っているが、どう選ぶかわからない」という状態に刺さる一冊だった。

各スタイルの特性・トレードオフを比較しながら選ぶための視点が得られ、設計判断の場面で「このシステムに本当に必要なアーキテクチャ特性は何か」から考えるクセがついた気がする。

ソフトスキルの章も含めて、アーキテクトという役割の全体像を掴みたい人にはおすすめの一冊。
