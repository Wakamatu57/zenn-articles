## はじめに

2026年9月に AWS Certified Developer - Associate（DVA-C02）に合格した。

本記事では、使った教材とその使い分け、勉強時間、本番を受けて感じたことをまとめる。これから DVA を受ける人、特に「書籍だけで足りるのか」が気になっている人の参考になればうれしい。

## 前提：受験前のスキル

- Web 系のフルスタックエンジニア（4年）。React / Next.js、Flask、PostgreSQL
- AWS は実務で使っている。構成は ALB + ECS（Fargate）+ RDS + S3 が中心。Fargate なのでサーバーレスといえばサーバーレスだが、Lambda、API Gateway、DynamoDB のようなイベント駆動のサーバーレス構成はあまり使っていない
- AWS SAA は取得済み（2022年）。ほかに情報処理安全確保支援士

AWS をまったく触ったことがない状態からのスタートではない点は、割り引いて読んでほしい。

## 結果と勉強時間

| 項目 | 内容 |
|------|------|

途中で業務が忙しくなって中だるみした時期があり、毎日コンスタントに進めたわけではない。

## 使った教材

### 書籍：AWS教科書 AWS認定デベロッパーアソシエイト テキスト＆問題集（EXAMPRESS）

試験範囲のサービスは、書籍でひととおり網羅できていた。DynamoDB、Lambda、API Gateway、SQS / SNS、Step Functions、CloudFormation / SAM、CodeシリーズにX-Ray、IAM や KMS まで、「この試験で何を問われるか」の全体像をつかむには十分だった。

ただし、**書籍の問題は知識問題が中心**だった。「このAPIの名前は？」「この設定項目は何をするもの？」という形の問題が多い。

### Udemy：【公式ドキュメント・全範囲カバー】DVA-C02日本語問題集 260問（詳細解説＋図解）

本番に近かったのはこちら。解き始めたときは、書籍の問題よりレベルがかなり高く、ギャップを感じた。本番の難しさは、この問題集と同じくらいだった。

本番は、短い知識問題よりも**シナリオを読んで構成を選ぶ文章題**が多かった。「最もコストを抑えられる方法は？」「開発工数が最も少ない方法は？」のように、条件付きで複数の正しそうな選択肢から1つを選ばせる問題だ。これはサービスの機能を知っているだけでは解けず、構成全体を理解している必要がある。

Udemy の問題集はこの形式の問題が多く、解説も「なぜ他の選択肢がダメなのか」まで書かれていたので、本番の練習として効いた。

## 進め方

```
① 書籍を1周（サービスの全体像をつかむ）
        ↓
② Udemy の問題集を1周（この時点で合格点には届いていた）
        ↓
③ 2周目は「分からなかった問題」と「合っていたけど自信がなかった問題」だけ解き直す
```

③ がポイントだった。1周目で正解していても、「たぶんこれかな」で選んだ問題がかなり多かった。それも含めると、結局**半分以上を見直した**。

1周目で解くときに、正解・不正解とは別に「自信がなかった」問題に印を付けておくと、2周目の対象をすぐ絞り込める。正解していても理解があいまいな問題は、本番で条件を少し変えられると落とす。

## 勉強して理解が深まった論点

試験問題そのものではなく、勉強中に「実務でも効く」と思った論点をいくつか挙げる。

### Lambda の権限は「Push型かPull型か」で決まる

- Push 型（S3 イベント通知、API Gateway、Cognito など）は、イベントソースが Lambda を呼び出す。なので **Lambda 関数のリソースポリシー**で呼び出し元を許可する
- Pull 型（SQS、DynamoDB Streams、Kinesis）は、Lambda がイベントソースをポーリングする。なので **Lambda の実行ロール**にイベントソースを読む権限を与える

「どこに権限を書くか」で迷ったときは、どちらが呼び出す側かを考えれば決まる。

### Lambda の Provisioned Concurrency

Lambda は、呼び出されたときに実行環境がなければ、ランタイムの起動・コードの読み込み・初期化処理から始める。これがコールドスタートで、その分だけ応答が遅くなる。

Provisioned Concurrency は、指定した数の実行環境を**あらかじめ初期化して待機させておく**機能。コールドスタートを避けられるので、応答時間の要件が厳しい API などに向いている。

- 設定はバージョンかエイリアスに対して行う（`$LATEST` には設定できない）
- 待機させている間も料金がかかる
- 似た話として、メモリを増やすと CPU も比例して増えるので初期化は速くなる。ただしデプロイ（コードのアップロード）の時間はパッケージのサイズで決まり、メモリは関係ない

### DynamoDB のセカンダリインデックスとホットパーティション

- 項目がどの物理パーティションに入るかは、**パーティションキーのハッシュだけ**で決まる。1つのパーティションには処理能力の上限があるので、キーの値が偏るとテーブル全体の容量に余裕があってもスロットリングされる（ホットパーティション）
- `Query` にはパーティションキーの指定が必須。別の属性で検索したいときにセカンダリインデックスを使う

| | LSI（ローカルセカンダリインデックス） | GSI（グローバルセカンダリインデックス） |
|------|------|------|
| パーティションキー | テーブルと同じ | 別の属性にできる |
| ソートキー | 別の属性にできる | 別の属性にできる |
| 作成できるタイミング | テーブル作成時のみ | いつでも追加・削除できる |
| 容量 | テーブルと共有 | 独自に持つ |
| 読み取りの整合性 | 強い整合性も選べる | 結果整合性のみ |

「ソートキー以外の属性で検索したい」なら、その属性を GSI のパーティションキーにするのが定石。

### CloudWatch のメトリクスフィルターでアラートを飛ばす

これは実務にすぐ持ち帰れた論点。CloudWatch Logs に出ているアプリのログから、特定の文字列に一致した行をメトリクスフィルターで数え、しきい値を超えたら CloudWatch アラーム → SNS でメールや Slack に通知する。

500 番のレスポンスの件数や応答時間なら ALB の標準メトリクスでアラームを設定できるので、メトリクスフィルターが活きるのは**アプリのログにしか出ない情報**を監視したいとき。たとえば、DB への接続エラーや外部 API の呼び出し失敗といった特定の例外が出たら通知する、といった使い方ができる。

### API Gateway の「統合レスポンス」と「ゲートウェイレスポンス」

- バックエンドまでリクエストが届いた場合の応答を整形するのが統合レスポンス
- 認証エラー（401）やスロットリング（429）など、API Gateway がバックエンドを呼ぶ前に返す応答を整形するのがゲートウェイレスポンス

見分け方は「バックエンドに届いたかどうか」だけ。

### CloudFormation のスタックポリシーと DeletionPolicy

- スタックポリシーは、更新時にリソースの置換や削除を**そもそも起こさせない**
- `DeletionPolicy: Retain` は、削除や置換が起きた**後に**実体だけ残す保険

本番の DB のように絶対に消したくないリソースには、両方を組み合わせる。

### KMS のエンベロープ暗号化

KMS のキー自体で大きなデータを直接暗号化するのではなく、`GenerateDataKey` で発行したデータキーで暗号化し、データキーは KMS のキーで暗号化して一緒に保存する。KMS のキーは「データを暗号化する鍵」ではなく「鍵を守る鍵」という理解が大事だった。

### Secrets Manager のローテーションの仕組み

1つのシークレットが複数のバージョンを持ち、`AWSCURRENT`・`AWSPENDING`・`AWSPREVIOUS` のラベルで切り替える。ローテーション用の Lambda は「新しい値を作る → 反映する → テストする → 切り替える」の4ステップで、テストに失敗すれば `AWSCURRENT` は古い値のまま残る。

### IMDSv2 で SSRF から認証情報を守る

`HttpTokens: required`（トークンなしの取得を拒否）と `HttpPutResponseHopLimit: 1`（トークンをインスタンスの外に出さない）の2つをセットで設定する。片方だけでは穴が残る。

## 振り返り：問題集だけでも合格はできると思う

正直、**試験に合格することだけが目的なら、Udemy の問題集だけでも足りる**と思う。解説が丁寧なので、問題を解きながらサービスを覚えていくこともできる。

それでも書籍から始めたのは、体系的に学んでいない状態で問題を解き始めるのが自分は嫌だったから。先に全体像をつかんでおくと、問題集の解説を読んだときに「どのサービスのどの話か」がすぐ頭の中で位置づけられる。このあたりは好みなので、自分に合う方を選べばよいと思う。

ひとつ反省があるとすれば、途中で業務が忙しくなって**中だるみした**こと。受験日を先に予約しておけば、もう少しペースを保てたと思う。

## まとめ

一番よかったのは、**普段の業務で使っていないサービスを知るきっかけになった**こと。

DVA で問われるのは、CloudFront、S3、API Gateway、Lambda、SNS、SQS、DynamoDB といったサーバーレスの構成が多い。一方で、自分の実務は ALB + ECS（Fargate）+ RDS + S3 の構成がほとんどなので、Lambda を中心にしたイベント駆動の設計にはあまり触れる機会がなかった。上で挙げた Lambda の Provisioned Concurrency や DynamoDB のインデックス設計のように、サーバーレスならではの考え方を知れたのは、今後の設計の選択肢を広げるうえでよかった。

試験対策としては次の3点。

- 書籍は**サービスの網羅**、問題集は**本番形式の練習**と役割が違う。本番の難しさは問題集と同程度で、書籍の問題だけでは足りない
- 本番は「最もコスト・工数を抑える方法」のような、構成を理解していないと解けない文章題が多い
- 問題集の2周目は、間違えた問題に加えて「自信がなかった正解」も解き直す

次は AWS Certified Security - Specialty（SCS-C03）に挑戦中。……なのだが、C03 は2025年12月に始まったばかりで、**C03 に対応した体系的な書籍がまだ見当たらない**。今回のように「まず書籍で全体像をつかんでから問題集」という進め方ができず、どうしようという感じだ（笑）。

今は、公式の試験ガイドの出題範囲をチェックリストにして、AI と壁打ちしながらサービスを理解し、細かい仕様は公式ドキュメントで裏を取る、という形で体系立てを自作している。この進め方がうまくいったかどうかも含めて、合格したらまた書きたい。
